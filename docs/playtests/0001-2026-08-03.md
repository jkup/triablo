## Context

Phase 3, first playtest since the playable build (PR #49) gained walls and
tile rendering (0460, decision 0034) and grid-walking monster chase (0380,
decision 0035). The renderer draws entity sprites (circles + life bars,
decision 0027) and the tile layer — but no skill or attack has any visual
representation: melee hits, cleave arcs, and ground-stomp bursts resolve
instantly in the sim (decisions 0018/0020) with life-bar changes as the
only on-screen evidence. Projectiles exist as entities (0260) and do
render, but the barbarian kit (keys 1–3: rend, cleave, ground-stomp —
decision 0033) is entirely melee, so a playing owner sees nothing move
when attacking. No "dungeon cleared" concept exists anywhere in core or
the client; the crawl scenario's completion is an invariant, not game
state. Relevant decisions: 0018 (effect geometry), 0027 (render contract),
0033 (keybinds), 0034 (tile palette).

### Reproduction notes

Item 2 verified by code reading, not misperception: `buildScene`
(packages/client/src/scene.ts) emits tile layer + entity sprites + life
bars only; melee `applyHit` resolves same-tick with no scene artifact.
The owner saw the system working exactly as built — the gap is real.

### Dispatcher recommendation on item 3 (for the owner's ruling)

Two-track: (a) **now** — juice the procedural renderer (item 2's task):
readable attack feedback in the existing vector language costs no assets,
is agent-buildable and shot-verifiable today, and pillar 1 explicitly
prefers clarity over fidelity; (b) **when you want fidelity** — AI-generated
sprite sheets fit this repo unusually well (sprites are static data files,
the content lane's specialty; the deterministic rasterizer can blit them),
but the known failure mode is style drift across generations. If you go
there: rule a style bible first (resolution, palette, view angle, the
plague-woodcut tone), generate in curated batches, and land sprite support
as its own client task with procedural shapes as permanent fallback. The
two tracks are independent — (a) should not wait for (b).
